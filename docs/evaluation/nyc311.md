# M10: Official NYC 311 service-request status evaluation

**Scope:** Run a reproducible local-agent status-lookup test using *actual published municipal records*. The target is New York City's official [311 Service Requests from 2020 to Present](https://data.cityofnewyork.us/d/erm2-nwe9), dataset identifier `erm2-nwe9`. NYC Open Data states there are no restrictions on using its Open Data. Follow the portal's additional terms, attribute NYC Open Data/311, and obtain any employer-specific approval required by your workplace.

Official sources:
- [NYC Open Data FAQ and reuse](https://www.nyc.gov/opendata/get-started/FAQs)
- [NYC Open Data terms](https://data.cityofnewyork.us/stories/s/Terms-of-Use/k9k7-3cje)
- [NYC 311 dataset and field descriptions](https://data.cityofnewyork.us/d/erm2-nwe9)

## What the benchmark actually tests

This evaluation uses a temporary *generated* AET FastAPI + LangGraph project, patching only its local test graph to route `service request status <numeric_id>` into a deterministic in-memory lookup. It asserts exact status reproduction, tool calls, unknown IDs and malformed requests. **No live AI model generates these answers.**

The external fetch queries solely `unique_key` and `status` ordered by descending request identifier, limiting results to 120 records by default. This bounded top-ID slice is not a random sample and may change as new records arrive or statuses are updated.

The report contains only aggregate status counts, accuracy, in-process request timings (median/p95/max), timestamp, source metadata and a SHA-256 fingerprint of the bounded sampled IDs/status pairs. Original request IDs are **never** printed, committed or uploaded. Raw records live in temporary process files that are removed at exit.

## Run locally (Windows PowerShell or Linux)

From the Agentic Engineering Toolkit repository root:

```powershell
python -m pip install -e ".[demo]"
python -m pip install -e "./packages/agent-quality-kit"
python -m pip install -e "./packages/agent-provider-contract"
```

To test the evaluator without any network calls:

```powershell
python scripts/evaluate_nyc311.py --synthetic-input tests/fixtures/nyc311_synthetic.json --queries 6
```

To fetch and evaluate **real NYC 311 public data** (requires network access):

```powershell
python scripts/evaluate_nyc311.py --live --limit 120 --queries 100 --json-out nyc311-aggregates.json
```

The `--live` flag is required to contact the official API; no implicit network calls occur during synthetic tests. The CLI refuses to overwrite existing reports. No credentials or personal data are required.

## GitHub Actions evidence

The required `ci` workflow runs synthetic NYC 311-format integration on **all four** Windows/Linux × Python 3.11/3.12 combinations, without contacting NYC Open Data.

A separate **manual-only** workflow, [`nyc311-live-optional`](../../.github/workflows/nyc311-live.yml), performs the bounded official API evaluation on Ubuntu Python 3.11. An authorised maintainer can select **Actions > nyc311-live-optional > Run workflow** when external public-data availability is acceptable. It requests at most 120 published status records, tests up to 100 queries and uploads **aggregate JSON only**. It is **not** a required pull-request or default-branch check; an outage of the public API cannot block the offline build.

Success in the optional workflow is evidence of an actual public-data evaluation. It is **not evidence of model semantic accuracy, production infrastructure speed, actual service-request freshness, cloud portability, employee adoption or saved developer hours**. If the official API is unavailable, that optional workflow should fail; do not quietly relabel synthetic data as public.

## Result interpretation

- **Known status correctness:** Exact equality against statuses supplied by the official NYC records at retrieval time, in an in-memory lookup.
- **Unknown ID:** Exactly one absent numeric ID must return not found with a tool call.
- **Malformed ID:** Must bypass tool routing and return the deterministic mock response.
- **Latency:** In-process TestClient + LangGraph graph + dictionary lookup; excludes network, concurrency, model inference, authorization, database/storage and full dataset ingestion.
- **Sampling:** This is a bounded *ordered* slice of a fixed historical period, not a representative random sample of NYC service requests. Avoid population-level generalization.
- **Data:** The API exposes only city-published request identifiers and statuses. Never expand the query to incident addresses, complaint bodies, caller descriptions or precise locations.

## Impact / KRA boundaries

Technical accuracy and latency on published public service-request statuses can support reproducibility claims about the toolkit's **deterministic routing and testing infrastructure**. They **cannot** prove LLM reasoning ability or the M8 human productivity reduction. Any employer-facing use should follow internal data/IP policy.
